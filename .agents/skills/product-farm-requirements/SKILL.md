# Требования Продуктовой фермы

## Вход и границы

Прочитай [AGENTS.md](../../../AGENTS.md) и применимые разделы [мастер-промпта](../../../МастерПромпт.md). Вход: запрос, текущие требования, доступные артефакты и стадия работы. Объём действий определяется A0.

## Процедура

1. Определи работу пользователя, сценарий и границу изменения. Разделяй пользователя фермы и аудиторию идеи по A1. Выпиши известное, допущения и требующее уточнения.
2. Присвой каждому атомарному требованию стабильный уникальный ID. Для нового реестра используй локальную конвенцию `PF-<раздел>-<номер>`, например `PF-10-001`; существующие ID сохраняй. Запиши источник (§ и пункт), владельца инструкции/skill и зависимости.
3. Для пользовательского/функционального требования заполни `priority`, `scenario`, `inputs`, `outputs`, `states`, `exceptions`, `acceptance criterion`. Для нефункционального — измеримый критерий и способ проверки. Приоритет требования не путай с приоритетом идеи из A5.
4. До реализации задай наблюдаемую приёмку: действие, результат, сохранённые данные, поведение при отказе. Свяжи её с существующими артефактами и проверками. Для спецификации укажи план проверки, не заявляй о пройденном тесте.
5. Раскрой применимые сценарии по таблице ниже. Остальные сохрани в общем реестре как вне текущего среза. Постоянные ограничения проверяй ссылками на A1–A10, без копирования текста.
6. При изменении требований оцени затронутые входы, версии и зависимые результаты по A4. Обнови реестр, документацию и журнал по A10; явно покажи расхождения с исходником.
7. При приёмке сопоставь каждое заявление с реальным прогоном, проверкой или артефактом. Раздели запланированное, реализованное, проверенное и заблокированное. Конечную готовность сверяй с каждым пунктом §48.

## Документация внутри сервиса (§42)

При создании/актуализации проверь девять групп:

1. Контекст: цель, пользователи, терминология, границы, допущения, архитектурные решения.
2. Реестр требований с ID и полями из процедуры.
3. Нефункциональные требования: persistence, authorization, privacy, accessibility, performance, background jobs, limits, calculation correctness, observability, maintainability; каждому — измеримый критерий и проверка.
4. Архитектура: C4 Context/Container, ключевые Component diagrams, data model/flow, роли, оркестрация, контракты, версии, восстановление.
5. Интеграции: provider/service, purpose, data sent, auth method, actual limitations, version, alternatives, metrics, failure behavior, ссылка на официальные ограничения.
6. Расчёт: baseline, метрики, datasets, формулы, статистика, допущения, параметры, единицы, пропуски, сценарии, ограничения, контрольные расчёты, measured vs modeled. Методика и результаты — из efficiency-calculation.
7. Поддержка: структура, dependency versions, setup/run/deploy, environment example, logs/errors, backup/restore.
8. Развитие: что меняется конфигурацией, а что кодом; условия необходимости дополнительных микросервисов, плагинов, MCP, отдельной очереди, Temporal, vector search и других расширений. Их описание не разрешает реализацию.
9. Материалы: открывающиеся ссылки на репозиторий, схемы и технические материалы.

## Результат и передача

Выдай реестр, сценарии и приёмку, карту «требование → владелец → артефакт/проверка», пробелы и изменения. Покрытие инструкциями не означает готовность реализации.

Контракты раскрывает [agent-step-contract](../agent-step-contract/SKILL.md), исследование и отчёт — [evidence-and-critical-assessment](../evidence-and-critical-assessment/SKILL.md), численные методики — [efficiency-calculation](../efficiency-calculation/SKILL.md). Не копируй их схемы и алгоритмы.

# Контракт агентного шага

Основа — [AGENTS.md](../../../AGENTS.md), A2–A8; источники — [мастер-промпт](../../../МастерПромпт.md), §§6–7, 15–16. Вход: роль, цель, событие запуска, версии данных, зависимости, разрешения и BudgetPolicy. Соблюдай текущую границу работ по A0.

## 1. Назначить ответственность

Для полного workflow отобрази все функции на шаги. Вводная §6 упоминает 12 агентов, но перечислены 13 функций; покрывай весь список. Объединение допустимо, если отдельно видны вход, ответственность и результат каждой функции. Объясни, какие функции объединены и почему.

| Функция | Вход → результат |
| --- | --- |
| Оркестратор | Идея, приоритет, ограничения, состояние → план, зависимости, вызовы, контроль лимитов |
| Аналитик идеи | Аудио, расшифровка → карточка, допущения, пробелы |
| Аналитик рынка | Карточка, поисковая задача → рынок, конкуренты, альтернативы, источники |
| Аналитик эффективности / прогнозист | Baseline, прогоны, тренды, допущения → методика, проверяемый расчёт, интервалы, сценарии |
| Стратег / визионер | Карточка, рынок, прогноз → варианты развития, ценностные гипотезы, противоречия |
| Бизнес-консультант | Варианты → применимость к процессу, ограничения внедрения, ценность |
| Продуктовый маркетолог | Аудитории, альтернативы, ценность → сегменты, позиционирование, гипотезы спроса |
| Исследователь | Гипотезы, прото-персоны → синтетические возражения, пробелы, план реальных проверок |
| UX-аналитик | Работы пользователя, ограничения → сценарии, состояния, UI-требования |
| Критик | Материалы ролей → слабые доказательства, контраргументы, противоречия, стоп-факторы, рекомендация |
| Трекер | Гипотезы, результаты → следующий наиболее полезный и дешёвый эксперимент, критерии перехода, метрики, контрольные точки |
| Агент реализации | Решение, спецификация, выбранная цепочка → MVP одного сценария |
| Редактор отчёта | Версии проверенных результатов → единый интерактивный отчёт |

## 2. Описать StepDefinition

Каждый шаг имеет все поля §7:

```text
id, version, role, goal, trigger,
input_schema, output_schema,
tools, permissions, dependencies,
entry_conditions, completion_conditions, validation,
timeout, retries, call_limit, token/computation_limit,
next_step_rules
```

Задай конкретные схемы и условия завершения. `token/computation_limit` означает обязательное ограничение токенов/вычислений; при выборе допустимого идентификатора в коде документируй соответствие. Согласуй ограничения шага с A8, инструменты/действия — с A3, A6–A7.

Проверь зависимости и условия входа: версии, обязательные данные, разрешения, готовность компонентов. В next_step_rules перечисли применимые ветви успеха, ошибки, ожидания, исчерпания лимитов и отмены; состояния бери из A5.

## 3. Выполнить и валидировать

До вызова проверь входную схему, entry_conditions, лимиты и зависимости. Собирай реальный учёт времени/вызовов, измерения и ссылки на артефакты.

Каждый результат содержит все поля:

```text
idea_id, run_id, step_id, input_version,
status, conclusion,
evidence[], assumptions[], errors[],
duration_ms, call_count,
measured_metrics[], artifact_refs[]
```

Пустые массивы допустимы по смыслу; отсутствие данных должно быть отражено в status/conclusion. Счётчики и метрики берутся из выполнения, не придумываются моделью.

Перед записью проверь output_schema, validation, completion_conditions, ID/версии и ссылки на артефакты. Повреждённый или некорректный ответ модели не сохраняй как нормальный результат и не передавай в отчёт. Сохрани безопасную диагностику ошибки; примени ветвь восстановления в пределах лимитов. Только проверенный результат завершает шаг и открывает зависимости.

## 4. Проверить управление и восстановление

Проверь применимые сценарии A4–A5: повтор запроса/команды, закрытие вкладки, перезапуск worker после сохранённого шага, retry упавшего шага, изменение входа, pause/resume/cancel, смена приоритета. Проверь повторное использование успешных независимых результатов и восстановление только из корректного checkpoint.

При нехватке данных применяй A6. Повторы и repair прекращаются при исчерпании лимита; причина остановки и доступное действие пользователя видимы.

## Результат и передача

Выдай StepDefinition, сопоставление функций/шагов, схему результата, правила переходов/восстановления, выполненные проверки или их план в фазе спецификации.

Содержание аналитических шагов задают [evidence-and-critical-assessment](../evidence-and-critical-assessment/SKILL.md) и [efficiency-calculation](../efficiency-calculation/SKILL.md); карточку, UX и приёмку — [product-farm-requirements](../product-farm-requirements/SKILL.md). Этот skill отвечает за выполнение, связанные skills — за смысл результата.

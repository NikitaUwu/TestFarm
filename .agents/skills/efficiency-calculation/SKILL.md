# Расчёт эффективности

Основа — [AGENTS.md](../../../AGENTS.md), A2–A4, A7–A8; источники — [мастер-промпт](../../../МастерПромпт.md), §§22–26, 32. Вход: версия идеи, baseline, DatasetVersion, варианты и их реальные прогоны/RunLog, пороги качества и эффекта, EffectModel, допущения. Выполняй только порученную фазу по A0; описание методики не требует запуска реализации.

## 1. Зафиксировать план и данные

Подготовь сравнение `Baseline vs Variant A vs Variant B` на одном сопоставимом EvaluationDataset. Варианты могут отличаться моделью, промптом, цепочкой или микросервисом; число и лимиты — A8. До прогонов задай требования к качеству. Пороги решения получай из evidence-and-critical-assessment, а не подбирай после просмотра чисел.

Для baseline сохрани источник, период, единицы, n, пропуски, долю пропусков, ограничения; нужна минимум одна основная метрика и одна метрика качества. Примеры: sec/task, correct%, manual-review%, throughput, successful completion%. Определи направление улучшения и единицы каждой метрики.

Проверь сопоставимость задач, версий dataset и условий. Сохрани сырые TaskObservation/Measurement, настоящие входы/выходы, ошибки, повторы и RunLog со связями по A4. Объяви обработку пропусков и исключений; не превращай отсутствующие значения в нули и не скрывай неудачные прогоны. Если данные не позволяют сравнение, укажи, чего не хватает, и не выдавай модельные числа за измерения.

## 2. Построить полную модель времени

Для последовательной обработки используй:

```text
T_total = T_input + T_preprocessing + T_ai + T_validation
        + T_manual_review + T_error_correction + T_retry
        + T_postprocessing + T_overhead
```

Для условного этапа используй ожидаемое значение, фиксируя вероятность и длительность. Для параллельных участков учитывай критический путь, а не сумму. В цепочке сервисов учитывай задержки, сеть, очереди, сбои и повторы. Не учитывай одно улучшение дважды через основную и производную метрику.

В EffectModel опиши формулы, параметры, единицы, источники и допущения, границы применимости. Не ограничивай итог временем ответа LLM.

## 3. Рассчитать измеренный эффект и неопределённость

Используй серверный расчёт по A2. Для сопоставимых наблюдений применяй парное сравнение; для времени по умолчанию — paired bootstrap. Пересэмплируй сопоставленные пары задач, сохраняя связь baseline/варианта. Повторения одной задачи не выдавай за независимые новые задачи; отрази способ их учёта.

Сохрани:

```text
method, sample_size, confidence_level, resamples, seed,
point_estimate, lower_bound, upper_bound,
assumptions, limitations, library_version
```

§25 приводит 10 000 resamples и 95% interval как пример параметров, а не неизменяемое требование. Выбери и зафиксируй параметры воспроизводимого расчёта. При подходящих условиях допустим доверительный интервал средней парной разницы; обоснуй выбор. Малую выборку, зависимость наблюдений и неприменимость метода покажи как ограничения, не маскируй произвольным «процентом уверенности ИИ».

Явно задай знак эффекта. Например, для времени `delta = T_baseline - T_variant`: положительное значение означает экономию времени; относительный эффект определяется только при допустимом ненулевом baseline. Это пример конвенции, выбранная формула должна быть зафиксирована в модели.

## 4. Отделить потенциал внедрения

Измеренный эффект получен на данных прогонов. Потенциальный эффект рассчитывается моделью внедрения и выдаётся отдельно.

Для потенциала обязательны сценарии `adverse`, `base`, `favorable`. Учти объём, качество ИИ, покрытие задач, ручную проверку, ошибки и исправления, retries, накладные операции и структуру цепочки. Для каждого параметра укажи значение, единицы, источник/допущение и применимый горизонт. Не умножай лабораторный выигрыш на весь объём без объяснения покрытия и внедрения.

Выполни SensitivityAnalysis минимум по объёму, качеству и доле ручной доработки. Покажи, какие параметры меняют знак/полезность эффекта и где выходят за пороги, переданные из оценки. Не добавляй смету разработки — A0.

## 5. Проверить и передать результат

Проверь единицы, формулы и воспроизводимость на контрольном расчёте с известным ожидаемым результатом. Для выбранной модели проверь существенные границы: пропуски, нулевой знаменатель, недостаточную выборку, ухудшение варианта, отсутствие различий, рост ручной доработки и параллельный участок. Выбирай проверки по применимости; не заявляй успешное выполнение, если создан лишь план.

Результат — CalculationRun со ссылками на входные версии, EffectModelVersion, сырые измерения, формулы/код, параметры статистики, интервалы, Scenario и SensitivityAnalysis. Отдельно представь качество, measured effect, modeled potential effect, пропуски, допущения и ограничения.

При новых наблюдениях выполни пересчёт по A4, укажи изменившиеся входы и численную разницу. Передай результат [evidence-and-critical-assessment](../evidence-and-critical-assessment/SKILL.md) для рекомендации; эта процедура не заменяет её правила решения. Графики и документацию проверь через [product-farm-requirements](../product-farm-requirements/SKILL.md); при выполнении как шага используй [agent-step-contract](../agent-step-contract/SKILL.md).

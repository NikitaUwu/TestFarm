# Эксплуатация

Версия: 2, 2026-09-09. Основной способ — Docker Compose из корня проекта; подробный вход — README.md. Web слушает 127.0.0.1:3000, API — 127.0.0.1:8000, остальные сервисы доступны только в Docker network. Для публичного развёртывания нужны HTTPS reverse proxy, защищённые cookies и отдельная проверка конфигурации; внешняя публикация сейчас не выполнена.

## Конфигурация

`scripts/setup.ps1` создаёт .env со случайными локальными паролями, если файл отсутствует. Не запускайте docker compose config без фильтрации вывода в публичный лог: он разворачивает секреты. Настройки продукта находятся в config/policies.json и config/prompts.json. При содержательном изменении повышайте версию соответствующего блока; уже запущенные исследования используют свой снимок.

Миграции выполняются сервисом migrate до API/Worker, защищены PostgreSQL advisory lock и журналом schema_migrations. Повторный запуск пропускает применённые файлы. Не изменяйте применённую миграцию — создавайте следующую.

### Аккаунты (изменение 2026-09-10)

Регистрация доступна на экране входа: логин (3–32 латинские буквы/цифры/точки/дефисы/подчёркивания, начало — буква/цифра), почта и пароль (12–200 символов). Логин и почта нормализуются в нижний регистр; пароль сохраняет регистр и пробелы. Это выбранные ограничения реализации, а не требования исходного мастер-промпта. Почтового подтверждения и восстановления нет.

Миграция 008 создаёт accounts; bootstrap переносит исходные principals в `admin` и `demo`, импортируя OWNER_PASSWORD/REVIEWER_PASSWORD только при отсутствии аккаунта. ID, идеи, старые сессии и пароли сохраняются. Повтор migrate не сбрасывает пароль; изменение переменных .env после импорта пароль аккаунта не меняет. Старым аккаунтам почта не назначается автоматически: они входят по логину. Новые аккаунты регистрируются через UI. Историческое поле principals.role оставлено для совместимости схемы; клиент его не выбирает и не получает, права определяются принадлежностью объекта.

Пароли: scrypt-v1, N=32768, r=8, p=3, случайная соль 16 байт, результат 32 байта. Сессия — случайный токен, в БД SHA-256 токена, cookie HttpOnly/SameSite=Strict на 12 часов. Все изменения, включая вход/регистрацию, требуют X-Farm-Request. Лимит входа: 50 попыток на адрес API-клиента за 5 минут и 10 на адрес+идентификатор; регистрации: 20 за час на адрес. При Vercel-проксировании адрес может быть общим: заголовки Forwarded не считаются доверенными. Для большой публичной аудитории нужен отдельно настроенный доверенный proxy/rate limiter.

Обновление существующей установки: `docker compose build api migrate web`, затем `docker compose up -d api web`. Проверка аккаунтов без вызовов ИИ: `docker compose run --rm api python -m tests.integration_auth` (создаёт и удаляет только свою временную БД; пользователь PostgreSQL должен иметь CREATEDB). Резервная копия PostgreSQL содержит аккаунты и хеши: хранить как приватные данные.

## Проверки и диагностика

```powershell
docker compose ps
docker compose logs --tail 80 api worker runner rules
docker compose run --rm api python -m unittest discover -s tests -v
```

Локальные численные/схемные тесты: `./scripts/test-python.ps1`. Для web: из каталога web выполнить `pnpm install --frozen-lockfile`, `pnpm typecheck`, `pnpm build`. Прямые версии Python закреплены requirements.txt, web — package.json и pnpm-lock.yaml. Полный список фактических Python-зависимостей закреплён в backend/requirements.lock.txt и используется Dockerfile. Для всей серверной тестовой группы предпочтителен Docker, где установлены httpx и остальные зависимости.

При waiting_for_user проверьте подключение, сохраните credentials в .env и пересоздайте API/Worker/Runner. Команда «Повторить» продолжает сохранённый запуск; изменение входов требует новой версии/исследования. После смены поставщика старый профиль намеренно отключён: создайте новый запуск с текущей конфигурацией. При отсутствующих данных не пытайтесь подменять результат моками.

## Резервная копия

Остановите пишущие сервисы: `docker compose stop api worker runner`. Снимите pg_dump в custom format внутри контейнера, затем docker cp в закрытый каталог резервных копий. Для MinIO остановите storage и сделайте файловую копию Docker volume objects. Возобновите сервисы после обоих снимков. Эти операции должны выполняться как согласованная пара, иначе PostgreSQL может ссылаться на отсутствующий объект.

Не используйте PowerShell текстовый pipeline для бинарного pg_dump. Пример безопасного экспорта:

```powershell
docker compose exec -T postgres pg_dump -U farm -d farm -Fc -f /tmp/farm.dump
docker cp product-farm-postgres-1:/tmp/farm.dump ./farm.dump
```

Для проверочного восстановления выполните `./scripts/restore-drill.ps1`: скрипт останавливает пишущие сервисы, создаёт согласованные pg_dump/objects.tar, восстанавливает новую БД и отдельный MinIO volume, сравнивает все строки и SHA-256 артефактов и возобновляет сервисы в finally. Проверка 9 сентября успешна: 47 таблиц, три файла. Файлы в .local/qa/restore-* и остановленная тестовая копия остаются для проверки оператором. Временный файл credentials удаляется. Рабочая БД не перезаписывается.

Скрипт также копирует остановленный volume runner_state в runner.tar, восстанавливает отдельный volume и сравнивает строки SQLite. Его нельзя заменять пустым, если требуется исключить повтор уже выполненного внешнего запроса. Финальная проверка: .local/qa/restore-20260909160444, две записи Runner, 47 таблиц PostgreSQL и три S3-объекта. Сохранность runner_state после SIGKILL дополнительно проверена integration_runner_restart.py. Не применяйте `--clean` к рабочей базе без отдельного разрешения.

`docker compose down` сохраняет volumes. `down -v` уничтожает данные и не является обычной остановкой.

## Аварийное восстановление и технические фикстуры

`scripts/worker-crash-drill.ps1` создаёт демонстрационный запуск, наблюдает его запрос Runner, аварийно завершает Worker и запускает его снова. Это намеренное прерывание фонового процесса; проводите отдельно от пользовательского исследования. Успешный результат 9 сентября: задание завершилось со второй попытки, 12 вызовов и 12 наблюдений без дублей. Выборка состояния до/после SIGKILL не доказывает точное попадание внутрь незавершённого внешнего вызова.

Для проверки восстановления перед расчётом и полного API сборки MVP используются `backend/tests/integration_worker_recovery.py` и `integration_mvp_queue.py`. Они требуют `TEST_RESTORE_DB` с префиксом `farm_restore_` и работают в восстановленной копии. MVP-тест создаёт искусственные отчёт и решение, явно помеченные как технические предусловия; затем выполняет реальные вызовы Groq и Runner. Не запускайте его с рабочей БД и не используйте его результаты как решение пользователя или доказательство бизнес-эффекта. Прикладной Worker получает DSN копии внутри теста, секреты в команду не подставляются.

Worker после checkpoint перед calculation/assessment/report продолжает работу без проверки доступности Groq; незавершённые research/experiments требуют доступного провайдера. Не удаляйте runner_state при восстановлении: он предотвращает повтор завершённых внешних запросов.

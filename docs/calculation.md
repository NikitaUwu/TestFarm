# Расчёт и входные данные

Реализация: backend/farm/calculation.py; версия метода и параметры сохраняются в EffectModel и CalculationRun.

## Dataset

JSON содержит name, source, period, provenance (`measured` или `demo`), labels и rows. Каждая строка: task_id, input, expected_label, baseline_seconds, baseline_correct, manual_review_seconds, error_correction_seconds. baseline_seconds и baseline_correct могут быть null: пропуски явно учитываются, нулями не заменяются. Метки задач должны принадлежать labels, ID задач уникальны.

Не размечайте придуманные данные как measured. Демо-набор никогда не даёт достаточного основания развивать идею. Источник и период должны описывать реальное происхождение baseline. Пороги качества/эффекта задаются до запуска, вместе с двумя или тремя промптами вариантов.

## Измерение и полное время

Runner сохраняет фактические входы и выходы ИИ/правил, время цепочки, время ИИ/правил, usage и версии компонентов. Каждый вариант проверяется на одном dataset, по умолчанию три повтора задачи.

Измеренный эффект цепочки = baseline − duration Runner. EffectModel v2: полное время = длительность цепочки + подготовка входа + ручная проверка при needs_review + исправление при неверном результате + обработка результата + накладные операции. Ручные этапы измеряются серверным таймером process_sessions с привязкой к задаче, варианту и DatasetVersion. Среднее фактических замеров заменяет оценку dataset для соответствующего этапа; demo не заменяет measured. Без замеров review/correction берутся из dataset, остальные неизвестные этапы отмечаются как ограничение. Нулевой замер допустим и отличается от отсутствия данных.

CalculationRun сохраняет полный снимок использованных process_sessions. Их изменение инвалидирует только расчёт и зависимые этапы. Прогноз и sensitivity используют те же замеренные ручные операции и накладные расходы. Пересчёт исторического запуска с EffectModel v1 явно фиксирует переход к v2; старые расчёты/отчёты сохраняются. Повтор ответа Runner не превращает время чтения кеша в длительность исходного эксперимента.

Общий total_time поддерживает условные операции (вероятность × длительность) и параллельные группы (критический путь). Пользовательский редактор произвольного графа времени пока отсутствует. Накладные операции ввода пользователя и очереди вне HTTP-цепочки не измерены; итог не объявляется измерением полного производственного процесса.

## Статистика

Повторы усредняются внутри одной задачи; n — число сопоставленных задач, а не число API-вызовов. Paired bootstrap пересэмплирует разности пар. По умолчанию 10 000 resamples, seed 42, percentile interval 95%. Сохраняются метод, n, параметры, версия NumPy, допущения и ограничения. При n < 2 интервала нет; при n < 10 вывод содержит предупреждение о нестабильности.

Положительная разница sec/task означает улучшение. Качество — доля правильных завершённых классификаций среди всех попыток; ошибки не исключаются. baseline_quality сохраняется отдельно. Демонстрационная происхождение наследуется результатом.

## Потенциал внедрения

hours/month = volume × coverage × (baseline − chain − manual_rate × review − (1 − quality) × correction) / 3600.

Сценарии adverse/base/favorable варьируют объём, качество и ручную проверку. SensitivityAnalysis содержит три оси. Объём по умолчанию 1000 задач/месяц и coverage 0.8 — допущения, не прогноз спроса. Все значения записываются в расчёт. Новые бизнес-наблюдения создают новый CalculationRun и Report; ID и источники наблюдений сохраняются. Историческое качество эксперимента не переписывается бизнес-наблюдением.

Контрольные примеры: пары 10/20/30 против 7/17/27 дают экономию 3 sec/task; baseline 10, chain 2, review 12 дают измеренную экономию 8 и модельное ухудшение −4. Нулевой объём даёт 0 hours/month. Проверки перечислены в [статусе](verification.md).

3. Пользовательская модель и основной пайплайн
В MVP используется одна пользовательская роль. Регистрация по ролям и owner/reviewer-разделение не проектируются. Пользователь вводит идею голосом или текстом, проверяет карточку, задает приоритет, запускает исследование и принимает решение после отчета.
Голос / текст-> STT, если голос-> редактируемая расшифровка-> структурированная карточка идеи-> приоритет HIGH / MEDIUM / LOW-> запуск в очередь-> Dispatcher-> Vercel Workflow-> анализ проблемы и аудитории-> рынок / конкуренты / внешние источники-> гипотезы и варианты решения-> baseline + реальные прогоны вариантов-> программный расчет эффекта и неопределенности-> сценарии / чувствительность-> критическая оценка-> отчет-> решение пользователя-> если «Развивать» -> работающий MVP
3.1. Работа при недостатке данных
Промежуточного пользовательского потока «дозапросить недостающие данные» нет. После запуска исследование по возможности проходит автономно. Агент использует данные идеи, внешние проверяемые источники, открытые наборы и примеры, прозрачные допущения и при необходимости явно синтетические демонстрационные данные. Если доказательств недостаточно, итогом становится «Недостаточно данных» или «Сначала проверить», а не обязательный вопрос пользователю.

Основная LLM - аналитический и генеративный движок внутри Vercel Workflow. Она не является оркестратором, базой данных, источником фактов или окончательным численным калькулятором.

4.1. Граница доверия к LLM
LLM не считается источником фактов. Значимые внешние утверждения должны быть основаны на реально прочитанных источниках. Числовые результаты эффективности должны быть получены программным расчетом.
5. LLM и STT: Царь Роутер
Царь Роутер фиксируется как единый внешний AI-провайдер для LLM и распознавания речи. Конкретные модели задаются конфигурацией, потому что состав бесплатных каналов может меняться.
TsarRouterClient  -> LLMProvider     -> Qwen, текущий основной бесплатный вариант  -> SpeechProvider     -> Whisper Large v3, бесплатный канал при наличии
Даже при одном внешнем API в коде сохраняются отдельные интерфейсы LLMProvider и SpeechProvider. Платный fallback не должен включаться незаметно.
6. Веб-поиск и внешние источники
Исследовательский агент сам решает, что искать, когда уточнить запрос и какие страницы читать. Поиск не является отдельным аналитическим модулем. Агенту предоставляются ограниченные веб-инструменты.
Research Agent / Qwen  -> web_search(query)     -> серверный инструмент     -> Tavily Search  -> read_page(url)     -> серверный инструмент     -> Tavily Extract     -> очищенный контент     -> обратно агенту
Qwen не обращается к Tavily напрямую. Модель формирует запрос на инструмент; сервер валидирует действие, применяет лимиты и политику безопасности, вызывает Tavily и возвращает результат агенту.
6.1. Контракт веб-инструментов
web_search({ query, maxResults, freshnessDays?, domains? })-> [{ title, url, snippet, publishedAt? }]read_page({ url })-> { url, finalUrl, title, text, publishedAt?, fetchedAt }
Веб-страницы считаются недоверенными данными, а не инструкциями агенту. read_page блокирует localhost, private IP и metadata endpoints, ограничивает redirect, размер ответа, тип контента и timeout.
7. Данные: Neon PostgreSQL + Vercel Blob
Neon PostgreSQL - единый source of truth для карточек, очереди, состояний, результатов исследований, журналов действий, измерений, расчетов, отчетов и MvpSpec. Vercel Blob хранит бинарные и крупные объекты.
Neon PostgreSQL  -> идеи и версии  -> jobs / research runs / step states  -> источники и утверждения  -> результаты прогонов и измерения  -> расчеты  -> отчеты и решения  -> MvpSpec / состояние MVP  -> ExecutionLogVercel Private Blob  -> audio  -> datasets  -> experiment artifacts  -> другие крупные файлы
Подключение Neon: @neondatabase/serverless + Drizzle ORM. Миграции: Drizzle Kit и SQL-файлы в репозитории. DATABASE_URL используется только на сервере; браузер не получает строку подключения.
8. Приоритетная очередь и запуск Workflow
Приоритетная очередь реализуется непосредственно в Neon/PostgreSQL. Отдельные Vercel Queues, Redis, Celery и постоянный worker не используются. Neon определяет, кто следующий; Dispatcher атомарно выбирает задачу; Vercel Workflow выполняет выбранное исследование.
Пользователь нажимает «Запустить»-> создается Job в Neon-> status = queued-> priority = HIGH / MEDIUM / LOW-> Dispatcher выбирает следующую Job-> status = starting-> запускается Vercel Workflow-> status = running-> completed / failed / cancelled-> Dispatcher запускает следующую Job
8.1. Dispatcher
Dispatcher - обычная серверная функция внутри того же Vercel-проекта, например dispatchNextResearchJob(). Она не работает постоянно. Вызывается при постановке новой задачи, а также после завершения, ошибки или отмены текущего Workflow.
dispatchNextResearchJob()1. Проверить, есть ли starting/running задача.2. Если есть - завершить без запуска.3. Если нет - найти лучшую queued задачу.4. Атомарно пометить ее starting.5. Запустить Vercel Workflow.6. После успешного старта пометить running.
8.2. Политика приоритетов
Базовое правило: HIGH выше MEDIUM, MEDIUM выше LOW. Внутри одинакового эффективного приоритета используется FIFO по queued_at.
priority values:LOW = 0MEDIUM = 1HIGH = 2
Чтобы LOW-задача не ждала бесконечно при постоянном появлении HIGH-задач, используется aging. Каждые 30 минут ожидания эффективный приоритет повышается на один уровень, но не выше HIGH. Исходный пользовательский priority при этом не меняется.
effectivePriority = min(HIGH, priority + floor(waitingMinutes / 30))LOW -> через 30 мин MEDIUM -> через 60 мин HIGHMEDIUM -> через 30 мин HIGHHIGH -> остается HIGH
Интервал aging хранится в конфигурации, например QUEUE_AGING_INTERVAL_MINUTES=30. Для демонстрации его можно временно уменьшить.
8.3. Конкурентный доступ и восстановление
Одновременно выполняется только одно тяжелое исследование. Захват следующей задачи делается атомарно в PostgreSQL, с блокировкой строки и подходом FOR UPDATE SKIP LOCKED или эквивалентной транзакционной логикой. Это не дает двум параллельным Dispatcher запустить одну и ту же задачу.
Статус starting используется как переход между захватом Job и реальным запуском Workflow. Если запуск Workflow не удался, Job возвращается в queued или после исчерпания попыток становится failed. Зависший starting старше заданного таймаута считается кандидатом на восстановление при следующем вызове Dispatcher.
Изменять приоритет имеет смысл только пока Job находится в queued. Позиция в очереди может показываться приблизительно и пересчитываться тем же алгоритмом, который использует Dispatcher.
9. Оркестрация: Vercel Workflow
Vercel Workflow заменяет LangGraph и отвечает за порядок крупных этапов, повтор после временных сбоев и продолжение фоновой работы независимо от открытой вкладки. Workflow получает идентификаторы, а состояние и результаты хранит в Neon.
researchIdeaWorkflow01 analyzeIdea02 analyzeAudience03 researchMarketAndEvidence04 buildHypotheses05 proposeVariants06 prepareBaseline07 runVariants08 calculateEffect09 buildScenarios10 criticalAssessment11 buildReport
Ошибка отдельного внешнего вызова сначала обрабатывается как ошибка действия: retry в пределах лимита, затем решение, можно ли продолжить с частичными данными. Job становится failed только если весь ResearchRun действительно не может продолжаться.
10. Расчетный модуль
Расчетный модуль фиксируется как небольшая Python Function в том же Vercel-проекте. Он использует NumPy и SciPy и выполняет детерминированные, воспроизводимые вычисления. Отдельный Python-сервер не нужен.
Vercel Workflow-> результаты baseline / Variant A / Variant B в Neon-> Python Calculation Function-> NumPy / SciPy-> CalculationResult-> Neon-> Qwen интерпретирует и критикует результат
Предпочтительный вызов: POST /api/calculate с calculationRunId. Python сам получает связанные наблюдения из Neon, выполняет расчет и сохраняет результат обратно. Большие массивы измерений через HTTP между модулями не передаются.
10.1. Что считается
Время: baseline_time, variant_time, абсолютная и относительная экономия.
Качество: quality_score / correct / success и проверка минимального порога качества.
Ручная доработка: manual_review_time, correction_time, manual_rework_rate, retry_rate.
Успешность: количество успешных задач и failures.
Полное время варианта должно учитывать AI, validation, review, corrections, retries и overhead, чтобы не завышать эффект.
10.2. Статистическая неопределенность
Если baseline и варианты проверяются на одном и том же наборе задач, используется парное сравнение. Базовый метод для временных метрик - paired bootstrap: 10 000 повторных выборок, 95% доверительный интервал, фиксированный seed=42. Параметры метода сохраняются вместе с результатом.
Если доверительный интервал включает отсутствие улучшения, отчет должен явно показывать неопределенность, а не утверждать однозначное улучшение.
10.3. Измеренный и потенциальный эффект
Измеренный эффект строится только по реальным наблюдениям на тестовом наборе. Потенциальный эффект моделирует применение при некотором объеме и других параметрах. Эти два результата не смешиваются.
MEASURED:реально измеренная разница времени / качества / ручной доработкиPOTENTIAL:объем задач * измеренный эффект на одну задачу * сценарные параметры
Для потенциального эффекта используются три сценария: негативный, базовый, благоприятный. Минимальная чувствительность проверяется по объему, качеству AI и доле ручной доработки. Сложная Monte Carlo-модель в MVP не требуется.
10.4. Происхождение чисел
Каждый важный параметр помечается по происхождению: MEASURED, EXTERNAL_FACT, CALCULATED, ASSUMED или SIMULATED. Это позволяет не смешивать измерения, внешние факты, расчеты и предположения.
Результат расчета сохраняет method, formula_version, seed, sample_size, inputs, results, scenarios, sensitivity и warnings. Для MVP часть структуры может храниться в JSONB.
11. Отдельно вызываемый сервисный компонент
Отдельных Vercel-проектов не будет. Для демонстрации отдельно вызываемого полезного компонента используется Rules & Validation Service внутри того же проекта, но с явным HTTP-контрактом и независимым журналированием вызовов.
POST /api/microservices/rules/runGET  /api/microservices/rules/healthGET  /api/microservices/rules/metadataLLM output -> Rules Service -> valid / violations / normalizedOutput
Компонент детерминированно проверяет структуру ответа, разрешенные значения и простые бизнес-правила. Это позволяет сравнивать «только LLM» и «LLM + правила» по ошибкам, повторным попыткам и ручной доработке.
Неопределенность: в строгой терминологии микросервис обычно предполагает независимое развертывание. Здесь используется отдельно вызываемый сервисный компонент в одном deployment. При необходимости его можно вынести позднее без изменения HTTP-контракта.
12. Создание MVP: MvpSpec + MvpRenderer
После решения «Развивать» агент формирует MvpSpec - структурированное описание одного пользовательского сценария. Универсальный MvpRenderer внутри фермы превращает эту спецификацию в работающий интерфейс. Отдельное приложение и отдельный deployment не создаются.
Decision: Развивать-> Qwen -> MvpSpec-> Neon-> /mvp/{id}-> MvpRenderer-> реальный ввод пользователя-> LLM / Rules Service / другой разрешенный компонент-> реальный результат
MVP не является статическим экраном: у него есть настоящий ввод, серверная обработка и результат. Vercel Sandbox не входит в обязательный контур.
Неопределенность: если проверяющий трактует «создание MVP» только как генерацию отдельного кода или приложения, MvpSpec может показаться слишком шаблонным. Это нужно проверить перед финальной сдачей.
13. Лимиты и журналирование
Лимиты соответствуют актуальным бесплатным тарифам внешних сервисов и задаются централизованной конфигурацией. Значения не должны быть жестко прошиты в бизнес-логику.
limits  -> max_llm_calls_per_run  -> max_search_calls_per_run  -> max_page_reads_per_run  -> max_retries  -> max_tokens_per_call  -> max_concurrent_research = 1
Основной журнал называется ExecutionLog. Он хранится в Neon и фиксирует наблюдаемые действия агентов, инструментов и системных модулей, а не скрытую цепочку рассуждений модели.
ExecutionLog  actor_type = agent | tool | system  actor_name  action  tool / provider / model  started_at / finished_at / duration  status  retry_number  usage  error  input_ref  output_ref
Примеры: market_researcher -> web_search; Tavily -> read_page; calculation -> paired_bootstrap; critic -> llm_call. Технические Vercel logs остаются вторым эксплуатационным уровнем. История исследования должна храниться в данных приложения и быть доступна независимо от временных платформенных логов.
14. Обновление UI и отображение прогресса
Real-time транспорт не критичен. Критично, чтобы пользователь видел текущий этап, последнее понятное действие и статус, а исследование не зависело от открытой вкладки. Для MVP используется polling раз в 2-5 секунд, целевое значение около 3 секунд.
Browser-> каждые ~3 сек. GET /api/research/{id}/status-> Neon-> { status, stage, progress, lastAction, ... }
SSE, WebSocket и live token streaming в первой версии не нужны. Workflow продолжает работу после закрытия вкладки; после повторного открытия UI восстанавливает состояние из Neon.

16. Осознанные упрощения
Роли доступа: одна пользовательская роль; сложная авторизация не проектируется.
Отдельная инфраструктурная очередь не используется; продуктовая очередь живет в Neon.
Одновременно выполняется один тяжелый Research Workflow.
Полный ERD сейчас не фиксируется; достаточно групп сущностей и ключевых связей.
Sandbox исключен из обязательного стека и вернется только при реальной потребности в исполнении произвольного кода.
SSE/WebSocket не используются; polling достаточен.
Отдельные сервисные проекты не создаются; используется один Vercel-проект.
Расчетный модуль ограничен воспроизводимыми базовыми метриками, paired bootstrap, тремя сценариями и простой sensitivity analysis.
17. Оставшиеся неопределенности и риски
Царь Роутер: конкретная бесплатная Qwen и бесплатный канал Whisper могут меняться. Модели и каналы задаются конфигурацией; платный fallback не включается незаметно.
Tavily: нужно подтвердить стабильность бесплатного доступа, регистрации и фактические лимиты для проекта. Реализация скрыта за WebResearchProvider.
Python/NumPy/SciPy на Vercel: требуется короткий технический spike сборки и выполнения выбранного calculation endpoint.
Rules component: один deployment может быть оценен как «не настоящий микросервис». При необходимости компонент можно вынести позднее, сохранив контракт.
MvpSpec: конфигурационный MVP минимизирует сложность, но перед сдачей нужно подтвердить, что такая реализация удовлетворяет требованию рабочего MVP.
Единая пользовательская роль - сознательное упрощение; если буквальная проверка ТЗ требует разделения доступа, придется вернуть минимальный контур авторизации.
Точные значения лимитов должны быть сверены с актуальными бесплатными тарифами непосредственно перед реализацией/демонстрацией.
18. Архитектурные инварианты
Один основной Vercel-проект; систему не дробить без реальной необходимости.
Neon PostgreSQL - источник истины о состоянии исследования, очереди и результатах.
Dispatcher выбирает следующую задачу; Vercel Workflow выполняет ее.
HIGH/MEDIUM/LOW + FIFO + aging определяют продуктовый порядок очереди.
Vercel Workflow управляет жизненным циклом процесса; LLM не управляет жизненным циклом приложения.
LLM не является источником фактов; внешние факты должны опираться на реальные источники.
Числовой эффект рассчитывается программно; LLM объясняет и критикует, но не подменяет вычисление.
Измеренный эффект и потенциальный эффект всегда разделяются.
Веб-инструменты имеют минимальные права; произвольный HTTP и секреты агенту не выдаются.
Провайдеры скрыты за интерфейсами; модели, каналы и лимиты задаются конфигурацией.
После запуска исследование по умолчанию автономно; отсутствие данных отражается в выводе, а не превращается в обязательный пользовательский опрос.
MVP должен иметь реальный ввод -> обработку -> вывод; статический макет не считается MVP.
Журналируется наблюдаемое действие агента, инструмента или системы, а не скрытая цепочка рассуждений модели.

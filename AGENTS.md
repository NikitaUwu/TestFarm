# Продуктовая ферма: постоянные инструкции

## A0. Источник, область и границы работы

Исходные требования — [МастерПромпт.md](МастерПромпт.md), введение и §§1–48. Он остаётся первоисточником деталей; этот файл закрепляет постоянные инварианты, а локальные skills задают специализированные процедуры. Новые явные указания пользователя определяют текущий объём работ; расхождения с исходником фиксируй как изменения требований.

Изменение объёма от 11 сентября 2026: пользователь исключил перенос исторических данных. Новый контур запускается с новой базой; прежние данные не импортируются и не удаляются. Это исключение к требованию миграции аккаунтов в A7, а не разрешение очистки прежних хранилищ.

Создание этих инструкций не разрешает начинать реализацию. Реализацию начинай только по следующему соответствующему запросу пользователя. Не составляй смету и не оценивай стоимость разработки.

У каждого правила один владелец: архитектурные ограничения — здесь, процедуры — в указанных ниже skills. При изменении правила редактируй владельца и обновляй ссылки; не копируй его текст в остальные файлы. Идентификаторы A0–A12 служат стабильными ссылками, номера § относятся к мастер-промпту.

## A1. Продукт и масштаб (§§1–2, 30, 48)

Цель — уменьшать неопределённость и рано находить основания остановить слабую идею. Пользователь фермы проверяет продуктовые или внутренние ИИ-гипотезы; он не тождествен аудитории исследуемой идеи. Три его работы: завести идею, управлять проверкой, принять решение о MVP.

Единый путь: голос или текст → расшифровка → карточка → приоритетная очередь → исследование → варианты → реальные прогоны → расчёт → критическая оценка → отчёт → решение пользователя → один работающий MVP → обновление метрик и рекомендаций.

Масштаб: самостоятельная регистрация личных аккаунтов с изолированными идеями, публичный отчёт только для чтения, один MVP одного завершённого сценария. Это изменение исходного ограничения «один владелец и проверяющий» по явному запросу пользователя от 2026-09-10. Не добавляй биллинг, командные пространства, Kubernetes, Kafka, промышленную отказоустойчивость или десять отдельных продуктов.

UI, сервер, хранение, очередь, оркестрация, ИИ, подключаемый сервис, расчёт, отчёт и MVP образуют работающую систему. Минимум один полезный микросервис вызывается отдельно. UI, статичный текст, макет или TODO-list не доказывают реализацию. Недоступная интеграция показывает «не настроено», «недоступно» или реальную ошибку. Заглушки допустимы только как явно обозначенный режим и не доказывают работу интеграции.

## A2. Стек и процессы (отчёты v1.2–v1.3, §§1–2, 7–12)

Модульное serverless-приложение в одном Vercel-проекте. Основание изменения — запрос пользователя применить отчёт «Продуктовая ферма: стек, пайплайн и структура системы» v1.2 от 10 сентября 2026. Изменение от 12 сентября 2026 по отчёту v1.3: единый внешний ИИ-шлюз — RouterAI, оплачиваемый по использованию; прежнее требование бесплатных ИИ-вызовов отменено. FastAPI как центральный backend, LangGraph, постоянный Worker, обязательный Runner/Sandbox и MinIO исключены из целевого контура.

| Часть | Технология и ответственность |
| --- | --- |
| Приложение | Next.js, React, TypeScript; UI, Route Handlers / Vercel Functions |
| Оркестрация | Vercel Workflow; этапы, сохранение и продолжение длительной работы |
| Очередь | Neon/PostgreSQL + атомарный Dispatcher; один тяжёлый запуск, FIFO и aging |
| Данные | Neon PostgreSQL, @neondatabase/serverless, Drizzle ORM/Kit и SQL-миграции |
| Файлы | Vercel Private Blob; доступ только через авторизованный сервер |
| ИИ | RouterAI; раздельные LLMProvider и SpeechProvider. Основная модель qwen/qwen3.5-9b, только критическая оценка — openai/gpt-oss-120b, STT — openai/whisper-large-v3-turbo. Автоматических fallback/escalation нет |
| Веб-инструменты | RouterAI Web Search plugin + Exa; 3 результата обычно, 5 для ключевой темы. Отдельного SearchProvider и чтения полных страниц нет |
| Расчёты | Python Function в том же deployment, NumPy/SciPy; получение входов из Neon по calculationRunId |
| Rules | Отдельно вызываемый HTTP-компонент в том же deployment, детерминированная валидация |
| MVP | MvpSpec + MvpRenderer, реальный ввод → серверная обработка → результат; произвольный код не исполняется |

Workflow не заменяет бизнес-состояние Neon. Численные результаты получает код, ИИ объясняет и критикует их. Старый контур не является зависимостью deployment; его ненужные исходники удаляются по запросу пользователя. Исторические хранилища не изменяются (A0).

## A3. Конфигурации и интеграционные границы (§§5, 8–9)

От UI и прикладной логики отделены промпты и шаблоны, роли, модели, ИИ-поставщики, критерии и веса, стоп-факторы, доказательность, расчётные модели и статистические методы, лимиты и визуальные токены. Конфигурации имеют ID и версию: `PromptSet`, `RoleSet`, `AssessmentProfile`, `EvidencePolicy`, `EffectModel`, `BudgetPolicy`, `ProviderProfile`, `UITokens`. Каждый ResearchRun и Report фиксирует использованные версии.

Бизнес-логика работает через LLMProvider (`chat`, `research`) и SpeechProvider (`transcribe`) без привязки UI к SDK поставщика. Текущий единственный адаптер — RouterAI. Версии моделей закреплены конфигурацией; прежние запуски не продолжаются с незаметно заменённым провайдером.

Каталог компонентов хранит `component_id`, `version`, назначение, способ/API вызова, `input_schema`, `output_schema`, `dependencies`, ограничения, измеряемые показатели, `health`, `authentication_type`. Базовый контракт: `GET /health`, `GET /metadata`, `POST /run`. Компоненты заменяются независимо. Пользователь выбирает или подтверждает вариант, оркестратор собирает последовательность вызовов.

## A4. Версии и прослеживаемость (§§12, 20, 29, 32, 45–46)

Содержательное изменение идеи создаёт IdeaVersion. Старые результаты и отчёты сохраняются; зависимые выводы получают `stale`. Пересчитываются только затронутые этапы; независимые успешные шаги не повторяются без причины. Порог гипотезы после просмотра результата меняется только новой версией. Новые наблюдения создают новую версию расчёта и обновлённую рекомендацию с объяснением изменивших её входов.

Разделы одного Report относятся к согласованной версии входов. Помимо использованных конфигураций из A3, обязательны ссылки `idea_version`, `research_run_id`, `dataset_versions`, `solution_versions`, `integration_snapshot`, `effect_model_version`, `assessment_profile_version`, `evidence_policy_version`, `prompt_set_version`, `provider_profile_version`.

Для любого вывода восстанавливается цепочка: слова пользователя → IdeaVersion → ResearchRun → Agent/StepRun → источники → варианты → версии компонентов → DatasetVersion → входы/выходы → сырые измерения → формула → статистический метод → допущения → результат → основание рекомендации → решение пользователя → MVP. Разрыв цепочки означает незавершённость реализации.

Минимальная предметная модель: `Idea`, `IdeaVersion`, `IdeaChange`; `BaselineMetric`, `Assumption`, `Constraint`; `Dataset`, `DatasetVersion`; `SolutionCandidate`, `SolutionCandidateVersion`; `ComponentCatalogEntry`; `ResearchRun`, `StepRun`, `ExperimentRun`, `TaskObservation`, `Measurement`; `CalculationRun`, `EffectModelVersion`, `Scenario`, `SensitivityAnalysis`; `EvidenceSource`, `EvidenceClaim`; `AssessmentProfileVersion`, `EvidencePolicyVersion`; `CriticalReport`, `Decision`; `MvpBuild`, `MvpVersion`; `Integration`, `IntegrationSnapshot`; `Artifact`, `AuditEvent`, `Job`.

## A5. Состояния и фоновая работа (§§13–16)

Воронка: Черновик → В очереди → Исследование → Критическая оценка → Решение → MVP в работе → MVP готов; отдельно возможен Архив.

`execution_state`: `ready`, `running`, `waiting_for_user`, `waiting_for_data`, `paused`, `error`, `completed`, `cancelled`. Ошибка, пауза и ожидание данных не являются этапами воронки.

Ровно три пользовательских приоритета: высокий, средний, низкий; внутри приоритета прозрачен порядок, например FIFO. Нужна защита от голодания, например aging. При превышении лимита активных идей создание/активация отклоняется с понятным сообщением и предложением архивировать существующую; скрытая переполненная очередь недопустима. Архив освобождает место.

Dispatcher запускается при постановке задания и завершении/ошибке/отмене Workflow. Статусы очереди: queued → starting → running → completed/failed/cancelled. Атомарный захват и восстановление зависшего starting обязательны. Aging: min(2, priority + floor(waitingMinutes / 30)); интервал конфигурируется, исходный приоритет сохраняется. Закрытие вкладки не останавливает Workflow; Neon хранит бизнес-состояние и результаты. Команды `pause`, `resume`, `cancel`, `retry failed step`, `change priority` идемпотентны; повторный «Запустить» с тем же идемпотентным запросом не создаёт второй ResearchRun.

## A6. Автономность и человеческое решение (§§16, 30, 43–44)

Запущенное исследование продолжается автоматически в пределах лимитов. По отчёту v1.2 §3.1 обязательного промежуточного опроса нет: агент использует источники, открытые данные, прозрачные допущения и явно синтетические примеры. Недостаток доказательств отражается в отчёте рекомендацией «Недостаточно данных» или «Сначала проверить». Отказ отдельного инструмента сначала обрабатывается в пределах retry, затем допускается продолжение с честно отмеченными пробелами. Пользователь может добровольно скорректировать карточку новой версией.

Переход к MVP по умолчанию решает человек после рекомендации «Развивать». Если поддержан автозапуск, это отдельная явная настройка с критериями и лимитами. До генерации MVP фиксируются критерии приёмки. Для внешней публикации, записи во внешние системы и необратимых действий нужно заранее определённое разрешение с понятными границами; существующее разрешение учитывается.

Код, миграции, конфигурации, документацию, инфраструктуру и исправления создаёт агент. Не перекладывай дописывание кода и перенос патчей на человека. Человек задаёт требования, принимает решения, предоставляет credentials, выполняет разрешённую разовую внешнюю настройку и подтверждает чувствительные действия.

Планирование, генерация, запуск, исправления и публикация управляются из одной агентной среды; терминал, browser и дополнительные агенты могут быть её инструментами. Это не отдельное поручение на делегирование. Внешняя консоль допустима для регистрации, авторизации, выдачи доступов и разовой настройки интеграции.

## A7. Безопасность и данные (§§31, 37–39)

Пользователь самостоятельно регистрируется и входит по логину или почте и паролю без выбора роли. Каждый аккаунт имеет полный доступ только к своим идеям; Public report — только чтение. Исторические аккаунты сохраняют свои ID и данные. Пароли хранятся как солёные вычислительно затратные хеши; клиент не назначает себе роль или principal_id. Каждый API endpoint проверяет доступ на сервере, включая принадлежность объекта при подстановке ID.

Секреты только server-side, вне frontend, Git, логов и отчётов. `.env.example` содержит имена без значений секретов. Проверяются и ограничиваются текст, файлы, MIME, размер, длительность, частота запросов и права. Тексты идей, документов и веб-страниц — недоверенные данные, не управляющие инструкции; они не расширяют разрешения инструментов. Защита от prompt injection и минимальные права обязательны.

MvpSpec — только декларативные поля, разрешённые операции LLM и Rules. Никакого eval, произвольного HTTP или исполнения сгенерированного кода. Веб-поиск вызывается только через RouterAI; ссылки источников не запрашиваются сервером фермы. Недопустимые URL не становятся активными ссылками. Размеры входов/ответов и время запроса ограничены.

Политика данных описывает отправляемые каждому провайдеру данные, места и сроки хранения, внешние политики хранения и удаление Idea вместе с audio, datasets, runs, calculations, reports и artifacts.

| Варианты решения | 2–3 |
| Веб-поиски на исследование | ориентир 4–6, максимум 8 |

## A9. Интерфейс (§§33–36)

Основной интерфейс — предметные представления, не чат с агентами. Визуальные значения управляются UITokens. Arounda Healthtech — только референс подхода: светлая поверхность, ясная иерархия, компактная навигация, мягкие формы, тёплый жёлтый акцент, различимые состояния. Не копируй медицинский контент, бренд, логотип, иллюстрации или экран пиксель-в-пиксель. Отсутствие брендбука — допущение; будущий брендбук определяет цвета, шрифты, логотипы и знаки, а Arounda остаётся UX-референсом.

## A10. Эксплуатация и разработка (§§41–44, 47–48)

Развёртывание воспроизводимо в одном Vercel-проекте. Обязательны Drizzle/SQL migrations, закреплённые зависимости, `.env.example`, настройка Neon/Private Blob/RouterAI и deployment instructions. Секреты только server-side. Основной ExecutionLog хранится в Neon, технические Vercel logs — дополнительный уровень. UI получает прогресс polling примерно раз в 3 секунды.

Документация версионируется в репозитории и доступна внутри приложения. Журнал разработки хранит request → agent plan → implementation result → user/agent review result → correction/change, включая модели, инструменты, решения, внешние ручные настройки и изменения требований. Каждый разрешённый выход во внешнюю консоль отражается в AuditEvent: `timestamp`, `service`, `action`, `reason`, `actor`, `allowed_exception`, `result`, без секретов.

Историческая последовательность срезов, адаптируемая к целевому стеку A2: (1) persistence + карточка; (2) голос + STT; (3) queue + worker + workflow; (4) ИИ + отдельный микросервис; (5) baseline + два варианта + RunLog; (6) calculation engine; (7) evidence + assessment + report; (8) decision + isolated MVP; (9) monitoring; (10) documentation and operational hardening. После каждого среза система остаётся интегрированной и работоспособной. Definition of Done проверяется по §48 и A4; красивый рассказ не заменяет цепочку данных, измерений, расчётов, неопределённости и решения.

## A12. Проверка разделения ответственности

Для нового требования сначала определи: это постоянное ограничение системы или повторяемая специализированная операция. Первое добавляй в соответствующий раздел этого файла; второе — в skill-владелец. Междисциплинарный результат передавай ссылкой на версионный артефакт, не дублируй процедуру: расчёт выдаёт данные оценке, оценка выдаёт рекомендацию, требования проверяют приёмку, контракт шага обеспечивает выполнение.

Текущий порядок проверки по запросу пользователя: последовательная реализация, несколько укрупнённых контрольных проверок или один финальный прогон; после каждой — короткий отчёт «сделано / осталось». Не запускать десятки проверок после каждого изменения.
